# `decision-map`: 큰 일의 결정 경로 밝히기

정확한 실행 계약: [`skills/decision-map/SKILL.md`](../../skills/decision-map/SKILL.md)

## 한마디로

한 번에 명세로 만들기 어려운 큰 일을 바로 구현 작업으로 나누지 않습니다. 먼저 목적지를 정하고, 지금 정확히 물을 수 있는 결정만 작은 문서로 만들어 하나씩 해결합니다.

```text
docs/decision-maps/<name>/
├── map.md
└── decisions/
    ├── D001-*.md
    └── D002-*.md
```

`map.md`는 전체를 빠르게 보는 인덱스입니다. 목적지, 현재 결정, 남은 결정, 아직 질문으로 만들기 어려운 영역, 범위 밖만 기록합니다. 질문의 근거와 상세한 해결 결과는 해당 `DNNN` 문서 한 곳에만 둡니다.

## 언제 필요한가요?

- 프로젝트가 한 세션보다 크고 무엇부터 결정해야 할지 불명확함
- 앞의 결정에 따라 뒤의 질문 자체가 달라짐
- 지금 모든 작업을 미리 나누면 추측성 티켓이 많아짐
- 명세를 쓰기 전에 제품·도메인·구조 결정을 단계적으로 확정해야 함

이미 요구사항과 결정이 충분히 명확하면 이 스킬 없이 바로 `to-spec`을 사용합니다.

## 어떻게 진행하나요?

한 번에 하나의 `Current` 결정만 처리합니다. 조사로 사실을 찾거나, 사람의 답을 받거나, 별도 허가된 작은 prototype으로 판단 근거를 만듭니다. 결정이 끝나면 상세 문서에 해결 결과를 기록하고 `map.md`에는 링크와 한 줄 요약만 추가합니다.

아직 질문을 정확히 말할 수 없으면 decision 문서를 억지로 만들지 않고 `Not yet specified`에 남깁니다. 앞의 결정으로 질문이 명확해졌을 때만 새 문서로 승격합니다.

열린 결정과 중요한 fog가 없어지면 `ready-for-spec`이 됩니다. 이때 `to-spec`에는 `map.md`와 실제 결정 문서들의 경로를 넘기며, 거대한 통합 요약 문서를 새로 만들지 않습니다.

## 하지 않는 일

- 구현 티켓이나 GitHub issue 생성
- 코드 구현 또는 목적지 산출물 완성
- 여러 에이전트의 claim·lease·동시성 관리
- 결정되지 않은 내용을 요구사항으로 확정
- commit, push 또는 게시

## 요청 예시

```text
$decision-map 결제 시스템 재설계처럼 아직 결정할 것이 많은 큰 작업을 로컬 결정 지도로 시작해 줘.
```
